## Как работает оформление

- «Оформление» доступно в общем меню до входа и в админке, в профиле студента, на странице загрузки APK и в ЛК продукта. Переключатель использует нативный `select` и его клавиатурное управление.
- `/theme-init.js` выполняется в `<head>` до загрузки React на всех трёх HTML-входах. Он читает `csu-schedule:appearance`, ставит `data-theme` и обновляет `theme-color`. Отсутствующее и неизвестное значение дают светлую тему. Если браузер блокирует хранилище, выбор действует до закрытия страницы.
- Вариант «Системная» отслеживает `prefers-color-scheme`. Ручной выбор сохраняется при изменении ОС и при выходе из учётной записи. Изменения синхронизируются между открытыми вкладками одного origin.
- Общие CSS-токены питают компоненты приложения и аналитики, график тоже использует общую палитру. `color-scheme` задаёт оформление нативных элементов браузера. Для вырезов и системных панелей CSS использует safe area браузера и значения Capacitor.
- В Android оформление значков статус-бара и системной навигации задают плагины Capacitor, уже входившие в приложение. Нативный экран запуска использует палитру ОС и остаётся до готовности кадра WebView. Аварийное ограничение ожидания составляет пять секунд. В веб-части выбранная тема применяется до появления интерфейса. [Системные панели Android](https://developer.android.com/develop/ui/views/layout/edge-to-edge) · [Готовность кадра WebView](https://developer.android.com/reference/android/webkit/WebView.html#postVisualStateCallback(long,%20android.webkit.WebView.VisualStateCallback)).
- Vite включает скрипт запуска в precache существующего Service Worker. В браузере проверена политика `script-src 'self'` и `style-src 'self'`. Статические файлы распространяются с того же origin.
- Внешняя карта осталась в исходном оформлении. Обрамление, навигация и загрузка используют тему приложения. В открытой документации ЧелГУ не нашёл параметра оформления для встраивания. [Описание навигатора ЧелГУ](https://www.csu.ru/press/news/studenty-chelgu-sozdali-virtualnyy-navigator-po-auditoriyam-dlya-abiturientov/).

### Как повторить

Из `frontend/` выполните `npm run build` и `npm test`, затем запустите `python tests/smoke_server.py`. Тестовые входы `fixture / fixture` для студента и `admin / fixture` для админки и аналитики.

- `node tests/responsive-browser.mjs` запускает Playwright. Через `PLAYWRIGHT_MODULE` можно указать путь к уже установленному `playwright/index.mjs`. Параметры `PLAYWRIGHT_CHANNEL=chrome`, `PLAYWRIGHT_ENGINE=webkit`, `SMOKE_ORIGIN` и `THEME_SCREENSHOTS` задают движок, адрес стенда и каталог скриншотов.
- Для `node tests/theme-pwa.mjs` запустите отдельный `smoke_server.py` с `SMOKE_PREVIOUS_DIST`, указывающим на `dist` предыдущей версии, и передайте соответствующий `SMOKE_ORIGIN`.
- Для Android после веб-сборки выполните `npm run cap:sync` и `gradlew.bat assembleDebug` из `frontend/android/`. Проверьте, что `VITE_API_URL` указывает на нужный тестовый API, если будете проверять авторизованные сценарии в APK.

## Границы проверки и риски

- Проверка WebKit выполнена на Windows. Safari на iPhone, Dynamic Island, нативная клавиатура iOS и установленная iOS PWA требуют устройства или Simulator. APK проверен на эмуляции Android 16 с жестовой навигацией. На старых Android и в режиме трёх кнопок поведение системных панелей требует отдельного запуска.
- Начальную заставку установленной PWA раскрашивает ОС по статическому манифесту. Нативная заставка Android следует ОС. Ручная настройка доступна веб-части после загрузки документа.
- Содержимое карты в браузерных тестах подменено локальным примером. Боевая доставка Moodle, Web Push и FCM и реальный импорт расписаний в этих проверках не использовались. Настройки сервера, ключи подписи, `applicationId`, версия APK и зависимости проекта сохранены.
- `origin/fix/responsive-audit` содержит отдельный `de77970`. В нём есть мобильное представление недели списком и дополнительные изменения клавиатурной навигации. Текущая работа сохраняет маршруты и представления основной ветки, исправляет обнаруженные на стенде переполнения и использует сценарии адаптивного аудита в браузерных тестах.
- `origin/feature/apk-build` содержит отдельный `ba16a58` с автоматическим адресом API в Capacitor и обработкой ответов без JSON. На `origin/master` Android-сборка по-прежнему берёт API из `VITE_API_URL`. Ветка также содержит старые коммиты версии и подписи. Эти расхождения требуют решения архитектора отдельно от оформления.

## Обновление и откат

1. Сохранить полный архив текущего фронтенда и собрать новый `dist` из проверенной ревизии. Перед выкладкой сверить `theme-init.js`, HTML-входы, `manifest.webmanifest`, `sw.js` и хешированные ресурсы как один комплект. Для боевого хоста сверить правила относительно корневых JS-файлов и заголовков CSP.
2. После согласования применить обычный порядок выпуска из [DEPLOY.md](DEPLOY.md). Опубликовать комплект фронтенда целиком. Проверить первый онлайн-запуск, обновление уже установленной PWA и офлайн-старт. Для выпуска Android использовать текущий API origin и ключ владельца. Версию Android согласовать перед сборкой релиза, чтобы обновление установилось поверх опубликованного APK.
3. Для отката сайта развернуть полный предыдущий архив фронтенда вместе с его Service Worker и ресурсами. После появления сети браузер получит замену работника. Оставить данные сайта и `localStorage` на устройстве. Для отката APK выпустить предыдущий проверенный код с текущей подписью и новым `versionCode`, чтобы Android допустил установку поверх обновления.
