## Цель

Понять, сколько людей пользуется приложением и как они до него доходят. Нужен
**ЛК продукта**: закрытая страница для разработчиков и менеджера продукта. Это
не админка методиста (`#/admin`): у ЛК свой адрес, свой вход и свои данные.

Первая версия отвечает на вопросы:
1. Сколько людей открыло лендинг → нажало «Войти через Moodle» → отправило форму → вошло (и почему не вошло).
2. Сколько скачали APK и сколько устройств реально его запустили.
3. DAU / WAU / MAU и всего пользователей.
4. Список пользователей и по каждому — когда заходил. Позже здесь же появятся его действия в приложении.

## Решения архитектора

### 1. Вход в ЛК продукта

- Отдельные переменные `PRODUCT_LOGIN` (по умолчанию `product`) и `PRODUCT_PASSWORD` (по умолчанию пусто). Пустой пароль — вход выключен, как у `ADMIN_PASSWORD`. Добавить в `Settings`, в `backend/.env.example` с комментарием.
- Новая роль `ROLE_PRODUCT = "product"` в `core/security.py`, функции `authenticate_product` и `require_product` по образцу админских. Пароль сравнивать через `secrets.compare_digest` (как у админа; если у админа иначе — сделай у обоих одинаково безопасно и отметь в отчёте).
- `POST /api/v1/auth/product/login` → `{access_token, expires_at}`, срок `JWT_TTL_HOURS`.
- Все эндпоинты ЛК — под `/api/v1/product/*`, только `require_product`. Админский и студенческий токены → 403. Продуктовый токен на `/admin/*` и `/me/*` → 403.

### 2. Таблица событий

Одна таблица `product_events` (модель `app/models/product_event.py`, миграция с `down_revision = "f2a4b6c8d013"`):

| поле | тип | примечание |
|---|---|---|
| `id` | bigint PK | |
| `occurred_at` | timestamptz | **время сервера** при приёме; время клиента не используем |
| `name` | varchar(64) | из списка ниже |
| `user_id` | FK users null, `ON DELETE SET NULL` | только из проверенного студенческого JWT, **никогда** из тела запроса |
| `device_hash` | varchar(64) null | `secret_hash(device_key)` из `services/feedback.py` (HMAC); сырой ключ не хранить |
| `platform` | varchar(8) null | `web` / `pwa` / `apk`; другое → null |
| `app_version` | varchar(32) null | версия сборки фронтенда, если клиент прислал |
| `props` | JSON null | задел на будущее, в этой задаче всегда null |

Индексы: `(name, occurred_at)`, `(user_id, occurred_at)`, `(device_hash)`.
Содержимое пользователя (тексты, заметки, пароли, логины) в события не пишется.

### 3. Список событий (белый список, `app/services/product_events.py`)

| `name` | Кто пишет | Когда |
|---|---|---|
| `landing_view` | клиент | показан экран `landing` (не чаще раза за открытие экрана) |
| `login_click` | клиент | нажата кнопка «Войти через Moodle» на лендинге |
| `login_submit` | клиент | отправлена форма входа Moodle (`MoodleLogin.tsx`) |
| `login_success` | **сервер** | успешный `POST /auth/moodle/login`, с `user_id` |
| `login_failed` | **сервер** | ошибка входа; причина в `props` не нужна — используй отдельные имена: `login_failed_auth` (неверный логин/пароль, `MoodleAuthError`), `login_failed_group` (`MoodleGroupError`), `login_failed_other` (прочие `MoodleError`, Moodle недоступен) |
| `app_open` | клиент | приложение открыто или вернулось на экран после 30+ минут в фоне (`visibilitychange`); метка последней отправки в `localStorage` |
| `apk_download` | клиент | открыта страница `/download` (там автоскачивание) |

`login_success`/`login_failed_*` сервер пишет в той же функции эндпоинта входа (`api/v1/auth.py`), `device_hash` — из `device_key` запроса, `platform`/`app_version` — из заголовков `X-Client-Platform`/`X-Client-Version`. Ошибка записи события не должна ломать вход (лог, без исключения наружу). Запись события при неудачном входе — отдельным коммитом после отката.

### 4. Приём событий от клиента

`POST /api/v1/events` — публичный:
- тело: `{device_key: str, platform?: str, app_version?: str, events: [{name: str}]}`, в пачке 1–20 событий; принимаются только клиентские имена из таблицы выше, неизвестные **молча пропускаются** (старые и новые клиенты не ломаются); серверные имена от клиента — тоже пропускаются;
- `Authorization: Bearer <студенческий JWT>` необязателен: валидный → `user_id`; отсутствует, истёк или чужая роль → событие без `user_id`, **не 401**;
- лимит: не больше 120 принятых событий в час на `device_hash` (настройка `PRODUCT_EVENTS_LIMIT_PER_HOUR`); сверх лимита — 204 и ничего не пишется (клиенту не нужно знать). Лимит по IP не делать: за прокси все студенты могут выглядеть как один адрес;
- ответ `204`. Эндпоинт синхронный и лёгкий: одна вставка пачкой.

### 5. Определение платформы на клиенте

Функция в `frontend/src/api/analytics.ts`: `Capacitor.isNativePlatform()` → `apk`; иначе `matchMedia('(display-mode: standalone)')` или `navigator.standalone` → `pwa`; иначе `web`. Версия — из `package.json` через `import.meta.env` (определи в `vite.config.ts` `define`). `api/client.ts` добавляет `X-Client-Platform` и `X-Client-Version` ко всем запросам. Отправка событий — `navigator.sendBeacon` недоступен с заголовком авторизации, поэтому обычный `fetch` с `keepalive: true`; ошибки сети игнорировать, не повторять, ничего не показывать пользователю. `device_key` — тот же `feedbackToken()` из `api/cache.ts`.

### 6. Метрики (сервер считает, фронт рисует — правило AGENTS №1)

Даты считаются в **часовом поясе Челябинска, фиксированно UTC+5** (константа в сервисе; не зависеть от TZ контейнера). «Активный пользователь за день» — студент (`user_id` не null) с хотя бы одним событием `app_open` или `login_success` в этот день.

`GET /api/v1/product/summary?days=30` (`days` из 1, 7, 30, 90; по умолчанию 30):
- `users_total` — студентов в `users`; `users_new` — созданных за период (`users.created_at`);
- `dau` (сегодня), `wau` (последние 7 дней, включая сегодня), `mau` (последние 30) — уникальные активные;
- воронка за период — **уникальные устройства** (`device_hash`) на каждом шаге: `landing_view`, `login_click`, `login_submit`, `login_success`; плюс `login_failed_auth`, `login_failed_group`, `login_failed_other` — число событий;
- `apk_downloads` — события `apk_download` за период; `apk_installs` — устройства, у которых **первое** событие с `platform=apk` попало в период; `apk_installs_total` — всего таких устройств;
- `by_platform` — активные пользователи за период по последней платформе;
- `daily` — массив за каждый день периода: `date`, `dau`, `new_users`, `landing_devices`, `login_success`.

`GET /api/v1/product/users?q=&group_id=&limit=50&offset=0&sort=last_seen|created` — студенты: `id`, `full_name`, `group` (`name`, `course`), `created_at`, `last_seen_at` (последнее событие пользователя, иначе `users.last_seen_at`), `active_days_30`, `last_platform`. `q` — поиск по ФИО без учёта регистра. Ответ с `total`.

`GET /api/v1/product/users/{id}/events?limit=100&before=<id>` — события пользователя от новых к старым: `occurred_at`, `name`, `platform`, `app_version`. Неизвестный пользователь → 404.

### 7. Страница `/statistic`

- Отдельная HTML-точка входа `frontend/statistic/index.html` по образцу `frontend/download/index.html`: добавить в `rollupOptions.input` (`vite.config.ts`), в `main.tsx` выбрать компонент по `location.pathname` (`/statistic`, `/statistic/`, `/statistic/index.html`), в `sw.ts` добавить `/statistic` в `denylist` навигации. Ссылок и кнопок на неё в приложении **нет**. `<meta name="robots" content="noindex">`.
- Компонент `frontend/src/pages/product/ProductStatistics.tsx`: форма входа (логин/пароль) → токен в `localStorage` отдельным ключом (по образцу сессии админа в `api/cache.ts`), выход.
- Экран: переключатель периода (сегодня / 7 / 30 / 90 дней); плитки чисел (всего пользователей, новые, DAU, WAU, MAU, скачивания APK, установки APK); воронка — четыре числа подряд с процентом перехода от предыдущего шага и строка с причинами неудачных входов; таблица по дням; список пользователей с поиском и пагинацией; клик по пользователю → его события («Вход», «Открыл приложение» и т. д. — русские подписи в `pages/product/labels.ts`).
- **Без новых зависимостей**: графики не нужны, таблицы и числа. Стили — в `styles.css`, ширина как у админки, мобильная вёрстка не обязательна, но без горизонтальной прокрутки страницы.
- Событие `landing_view` и пр. **не** пишутся для самой страницы `/statistic`.

### 8. Где ставить клиентские события

- `landing_view` — `Landing.tsx` при монтировании.
- `login_click` — обработчик кнопки «Войти через Moodle» на лендинге (только если пользователь не вошёл; «Открыть приложение» — не событие).
- `login_submit` — `MoodleLogin.tsx` при отправке формы.
- `app_open` — один раз в `App.tsx` при старте и при возврате на вкладку (правило 30 минут), **и для вошедших, и для гостей**; у вошедших запрос идёт со студенческим токеном.
- `apk_download` — `AndroidDownload.tsx` при монтировании.

## Тесты (до кода)

Бэкенд (`tests/test_product_stats.py`, SQLite, без реального Excel и сети):
- вход ЛК: верный пароль → токен; неверный → 401; пустой `PRODUCT_PASSWORD` → вход выключен; админский и студенческий токены на `/product/summary` → 403; продуктовый на `/admin/catalog` и `/me` → 403;
- `/events`: без токена → событие без `user_id`; со студенческим → `user_id` из токена, а `user_id` в теле игнорируется; с просроченным/админским токеном → 204, без `user_id`; неизвестные и серверные имена пропущены; 21 событие в пачке → 422; лимит на устройство срабатывает; сырой `device_key` в БД отсутствует;
- вход Moodle (подменить `MoodleClient`, как в `tests/test_moodle.py`): успех → `login_success` с `user_id` и `device_hash`; `MoodleAuthError` → `login_failed_auth`; `MoodleGroupError` → `login_failed_group`; поломка записи события не ломает вход;
- метрики: события, заведённые в тесте с нужным `occurred_at`, дают ожидаемые DAU/WAU/MAU; событие в 23:30 UTC относится к **следующему** дню по Челябинску; воронка считает уникальные устройства (два `landing_view` с одного устройства = 1); `apk_installs` считает устройство один раз по первому событию;
- `/product/users`: поиск по ФИО, сортировка, `total`; `/users/{id}/events` — порядок и `before`.

Фронтенд: `npm test` (добавить тест функции определения платформы и правила 30 минут, если они выделены в чистые функции — так и сделай), `npm run build`.

## Отчёт

Сделано по спецификации, отличия:
- `landing_view` пишется из `App.tsx` при переходе на экран `landing`, а не из `Landing.tsx`: в `Landing` нет хуков, тест `navigation-actions` вызывает его как функцию.
- `login_submit` отправляется сразу (`track(name, true)`), чтобы в ленте пользователя он стоял до `login_success`.
- Ответ событий пользователя — `{user, items, next_before}`.

Проверка:
- бэкенд: `.venv\Scripts\python -m pytest -q` — 289 passed (новые — `tests/test_product_stats.py`, 18);
- фронт: `npm test` — 16 passed (новый `tests/analytics.test.mjs`; в загрузчик `navigation-actions.test.mjs` добавлены заглушки `import.meta.env` и таймеров), `npm run build` — успешно, в `dist` есть `statistic/index.html`;
- миграция `a7d9e2c4b816`: upgrade → downgrade → upgrade на SQLite. На Postgres не проверялась — Docker не был запущен. Полная цепочка с нуля на SQLite не проходит из-за старой миграции `e8c1b2a3d4f5` (только Postgres) — не связано с задачей;
- вручную на локальном стенде (SQLite, mock Moodle): лендинг → «Войти» → форма → вход, события в БД с платформой и версией, `/statistic` — вход, сводка, воронка, список, карточка студента; ширина 375px без горизонтальной прокрутки. Ответы `/product/*` — 10–15 мс.

Новые переменные: `PRODUCT_LOGIN`, `PRODUCT_PASSWORD`, `PRODUCT_EVENTS_LIMIT_PER_HOUR` (в `backend/.env.example`).

Что учесть при выкладке:
- `alembic upgrade head`; задать `PRODUCT_PASSWORD`;
- хостинг должен отдавать `/statistic/` из сборки (как `/download/`);
- установки APK начнут считаться только после пересборки APK с этим кодом;
- `app_version` — из `frontend/package.json` (сейчас `0.1.0`), а не `versionName` APK; при выпуске версий стоит поднимать оба.

Замечено, не исправлялось: `moodle.py` пишет `device_key` в `users.device_key_hash` без хеширования; «сегодня» в расписании считается по TZ сервера.

## Вторая версия (20.11.2026)

По просьбе пользователя:
- период — пресеты (сегодня, 7, 30, 90 дней, год) и свои даты; `GET /product/summary?start=&end=` вместо `days`, до 731 дня; DAU / WAU / MAU — на последний день периода;
- графики на SVG без библиотек (`frontend/src/pages/product/charts.tsx`): линейный по дням (легенда-переключатели, перекрестие с подсказкой, вид таблицей), столбчатая воронка, полосы «чем пользуются» и платформ; палитра проверена валидатором (категориальная, 4 цвета; у двух контраст < 3:1 — поэтому есть табличный вид);
- вкладка «Пользователи» (`#/users`): поиск, группа, даты последнего захода и первого входа, сортировка; карточка `#/users/ID` со счётчиками по событиям и лентой действий (по времени, у сообщений — заголовок);
- новые события: `schedule_day_view`, `schedule_week_view`, `map_open`, `help_open`, `push_open` (клиент); `message_received`, `message_read`, `message_ack`, `push_sent`, `push_subscribed`, `note_saved`, `feedback_sent` (сервер, события сообщений — в той же транзакции);
- удержание (1/2/4 неделя после первого входа) и охват групп; доля студентов с push;
- ЛК вынесен в отдельный чанк (`React.lazy`), студенческое приложение не тянет его код.

Проверка: бэкенд — 302 passed; фронт — 18 passed, `npm run build` успешно; в браузере на Docker-стенде с Postgres и демо-данными — обзор, свой период, фильтры пользователей, карточка, лента; события экранов приходят из приложения.

Замечено и исправлено попутно: лента действий сортировалась по id, а не по времени; токен удалённого студента ронял бы `/events` на внешнем ключе — теперь событие пишется без пользователя.
