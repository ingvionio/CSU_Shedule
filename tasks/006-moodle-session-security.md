# 006 — Шифрование и жизненный цикл Moodle-сессий

## Поручение

Требования согласованы пользователем в интервью grilling; реализация подтверждена.

- Одна общая серверная сессия на пользователя для всех устройств.
- Cookies и sesskey хранятся только под AES-256-GCM. Пароль Moodle не сохраняется.
- MOODLE_ENCRYPTION_KEY — обязательный отдельный случайный ключ из 32 байт в base64; без него сервер не запускается. JWT_SECRET не используется для шифрования.
- Сервер поддерживает живую Moodle-сессию через core_session_touch по расписанию с учётом sessiontimeout Moodle, в том числе при закрытом приложении. На каждое действие пользователя запрос в Moodle не отправляется.
- Авторизация действует 120 часов после последнего использования видимого приложения. Фоновые запросы приложения и keepalive Moodle этот срок не продлевают.
- По истечении срока доступ блокируется сразу; секреты удаляются не позднее часа. Профиль, сообщения и задания сохраняются.
- Сетевая ошибка Moodle не отзывает действующую авторизацию приложения. Подтверждённая утрата Moodle-сессии требует нового входа; без пароля восстановить её нельзя.
- Явный выход отзывает общую сессию на всех устройствах и удаляет её секреты. Общий серверный ключ сохраняется.
- Переход удаляет старые секреты и отзывает старые студенческие JWT. Вход/продление через регистрацию по ФИО и группе закрывается.
- Изменения включают Alembic-миграцию, фронтенд, тесты и отчёт. Без коммита.

## Вопросы к архитектору

Открытых вопросов по согласованному объёму нет. Версия и sessiontimeout рабочей инсталляции Moodle не проверялись; используются ответы Moodle, а не предположение о трёхчасовом сроке. Гарантия сохранения входа не распространяется на принудительный отзыв сессии Moodle или недоступность дольше её idle timeout.

## Отчёт

Выполнено в ветке `refactor/moodle-session-security`, без коммита.

### Реализация

- `backend/app/core/crypto.py`, `config.py`: AES-256-GCM с новым случайным nonce из 12 байт на каждую запись. Дополнительные аутентифицируемые данные привязывают шифротекст к ID пользователя и типу секрета. Ключ принимается только как base64 ровно 32 байт, обязателен, скрыт в представлении настроек и сообщениях валидации. Вывод из JWT_SECRET удалён.
- `backend/app/models/user.py`, `services/moodle.py`: пароль больше не принимается сервисом сохранения и не хранится в модели. Cookies и sesskey записываются в отдельные зашифрованные текстовые поля. Ключ устройства сохраняется как хеш. Повторный вход активного пользователя с другого устройства сохраняет общую сессию приложения; после отзыва или истечения создаётся новый идентификатор, старые токены не оживают.
- `backend/app/services/moodle_sessions.py`: отдельная отметка активности, срок строго 120 часов, очистка секретов и общий отзыв. `last_seen_at` профиля не используется для расчёта срока. Проверка срока и существования сессии выполняется сервером на каждом защищённом запросе.
- Worker запускается и останавливается через lifespan FastAPI (`backend/app/main.py`). Проверка очереди — каждые 5 секунд. Для продления используется половина полученного таймаута Moodle, но не больше часа; до истечения пользовательских 120 часов worker работает и при закрытом приложении. Просроченные данные очищаются перед обработкой очереди. Обработка ограничена 4 потоками и 200 сессиями за проход. Атомарная аренда строки на минуту защищает от дублирования запросов между процессами API. Во время сети транзакция не удерживается; ответ применяется только к прежней версии cookies и идентификатору сессии.
- `MoodleClient` получает sessiontimeout из уже загруженного HTML. Если его нет, отправляет один пакет AJAX `[core_session_touch, core_session_time_remaining]`. Такой же пакет используется при дальнейшем продлении. Сохраняются актуальные cookies ответа. Сетевые ошибки, некорректный ответ и ошибки службы не отзывают доступ; явные ошибки авторизации, HTTP 401 и перенаправление на форму входа отзывают сессию. Секреты/URL с sesskey не выводятся в новых диагностических сообщениях.
- `backend/app/core/security.py`, `api/v1/auth.py`, `schemas/student.py`: студенческий JWT связан с серверной сессией через `sid`. Старые JWT без `sid` отвергаются. `POST /auth/student/refresh` обновляет токен; только явный `active: true` отмечает использование. Для refresh и выхода допускается истёкший JWT с правильной подписью, но серверная сессия обязательно должна оставаться действующей: это позволяет устройству вернуться в общую сессию, которую поддерживали с другого устройства. Обычные защищённые запросы по истёкшему JWT запрещены. Выход удаляет секреты и отзывает все токены общей сессии. Админская авторизация сохраняет прежний контракт.
- `/auth/student/register` всегда отвечает 410. Удалены резервные сервис регистрации и схема ввода ФИО/группы (`services/students.py`, `schemas/student.py`).
- `frontend/src/api/student.ts`, `client.ts`, `cache.ts`, `App.tsx`: обновление по серверной сессии вместо повторной регистрации; открытие/возврат, нажатия, ввод и прокрутка видимого приложения отправляют отметку активности не чаще раза в минуту. Периодические API-запросы, таймер проверки истечения и серверный keepalive её не отправляют. Параллельные обновления объединяются; запоздалые ответы не восстанавливают выход и не перезаписывают другой вход. Запрос пользователя не повторяется от имени другой учётной записи. Выход подтверждается сервером; при сетевой ошибке показывается ошибка с возможностью повторить действие.
- `frontend/src/api/queries.ts`: кэш инбокса разделён по ID пользователя, чтобы смена учётной записи не показывала сообщения предыдущего пользователя. `pages/messages/StudentMessages.tsx` больше не предлагает резервный вход по ФИО; `pages/MoodleLogin.tsx` сообщает, что пароль не сохраняется.
- `backend/.env.example`, `docker-compose.yml`: обязательный отдельный ключ, параметры Moodle и пример генерации. Новых зависимостей нет.

### Миграция

`backend/migrations/versions/f3b5c7d9e124_moodle_sessions.py`, `down_revision = f2a4b6c8d013`.

Миграция очищает старые cookies, sesskey, зашифрованные пароли и сроки, удаляет старые столбцы, добавляет зашифрованные поля, идентификатор сессии, отметку активности и расписание продления. Все студенты после перехода входят повторно. Профили и связанные данные сохраняются. Откат схемы также очищает новые сессии и не восстанавливает прежние секреты.

### Запуск после проверки архитектором

Один раз сгенерировать ключ и сохранить как `MOODLE_ENCRYPTION_KEY` в окружении сервера или в `backend/.env`. Docker Compose читает `backend/.env`. Ключ не записывать в БД или Git. Пример генерации из `backend/`:

```powershell
.venv\Scripts\python -c "import base64,secrets; print(base64.b64encode(secrets.token_bytes(32)).decode())"
.venv\Scripts\python -m alembic upgrade head
.venv\Scripts\python -m uvicorn app.main:app --reload
```

Команду миграции выполнять с настроенным ключом и правильным DATABASE_URL, остановив старую версию сервера. Для запуска через Docker указать ключ в `backend/.env`. После обновления схемы запустить новую версию API и пересобранный фронтенд. Пользователям потребуется повторный вход. Сам ключ при выходе/очистке пользователя не удаляется; смена ключа делает прежние зашифрованные сессии нечитаемыми и требует нового входа.

### За рамками поручения

Публичные справочники и API расписания (`api/v1/public.py`) остаются публичными, как в исходной реализации; авторизация закрывает личные сервисы и студенческий интерфейс. Существующее сопоставление старых профилей по ФИО при первом Moodle-входе не менялось. Эти решения требуют отдельного поручения при необходимости пересмотра.

Основание механики keepalive: официальные исходники Moodle [session manager](https://github.com/moodle/moodle/blob/MOODLE_405_STABLE/lib/classes/session/manager.php#L779), [AJAX session API](https://github.com/moodle/moodle/blob/MOODLE_405_STABLE/lib/classes/session/external.php#L52), [экспорт sessiontimeout](https://github.com/moodle/moodle/blob/MOODLE_405_STABLE/lib/classes/output/requirements/page_requirements_manager.php#L294).
