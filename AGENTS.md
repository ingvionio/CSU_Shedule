# AGENTS.md — Расписание ИИТ ЧелГУ

Инструкции для Codex. Читай целиком перед любой задачей.

## Роли

- **Архитектор** (Claude вместе с Лёшей) — пишет требования, решает спорные места, ставит задачи в `tasks/`, принимает результат и коммитит.
- **Ты (Codex)** работаешь в одной из двух ролей — какой именно, сказано в начале поручения:
  - **исполнитель задачи** — пишешь код по файлу задачи `tasks/NNN-*.md`;
  - **помощник по поручению** — только читаешь и докладываешь (раздел «Поручения на чтение»).
- В обеих ролях не меняешь требования и не принимаешь продуктовых решений.

Если в задаче или документах неясность, противоречие или чего-то не хватает — **не придумывай**. Запиши вопрос в раздел «Вопросы к архитектору» файла задачи и сделай только то, что однозначно.

## Источники правды (в порядке приоритета)

1. Файл текущей задачи `tasks/NNN-*.md`.
2. `04-current-state.md` — что сделано и принятые решения.
3. `02-architecture.md`, `03-schedule-json.md` (контракт JSON недели), `05-feedback.md`, `06-messages.md`.
4. `backend/README.md`, `frontend/README.md`.

Документы (`*.md` в корне и README) **не редактируй**, кроме файла своей задачи: их правит архитектор.

## Продукт

Расписание Института информационных технологий ЧелГУ: бэкенд собирает неделю группы из постоянных пар (Excel) и временных изменений, фронтенд (React PWA) только рисует готовый JSON. Студент входит через Moodle; методист (админ) вносит изменения, пишет сообщения, отвечает на обращения.

## Стек

| Часть | Технологии |
|---|---|
| Бэкенд | Python 3.12, FastAPI, SQLAlchemy 2 (синхронный), Alembic, Pydantic v2, openpyxl, pytest |
| БД | PostgreSQL 16 в Docker; тесты — на отдельном SQLite-файле |
| Фронтенд | React 18 + TypeScript + Vite, TanStack Query, vite-plugin-pwa |

Новую зависимость добавляй только если задача этого требует, и укажи её в отчёте.

## Структура

```
backend/app/
  api/v1/      роутеры FastAPI (тонкие: разбор запроса → сервис → ответ)
  services/    логика: парсеры Excel, импорт, сборка недели, изменения, сообщения…
  models/      модели SQLAlchemy
  schemas/     схемы Pydantic (контракт API)
  core/        настройки, БД, безопасность, шифрование
  cli.py       консольные команды (python -m app.cli …)
backend/migrations/   Alembic
backend/tests/        pytest
frontend/src/         api/ (клиент, типы, хуки), pages/, ScheduleComponents.tsx, App.tsx
tasks/                задачи от архитектора
```

## Команды (PowerShell, из `backend/`)

```powershell
.venv\Scripts\python -m pytest -q                 # тесты бэкенда (SQLite, Docker не нужен)
.venv\Scripts\python -m alembic upgrade head      # миграции (нужен Postgres из docker compose)
cd ..\frontend; npm run build                     # проверка типов и сборка фронтенда
```

`.venv` создаётся так: `uv venv .venv --python 3.12; uv pip install -p .venv -r requirements-dev.txt`.

## Правила (нарушать нельзя)

1. **Бэкенд отвечает за корректность.** Отбор пар по неделям, применение изменений, сортировка — на сервере. Фронт ничего не вычисляет, только рисует.
2. **Парсеры Excel — чистые модули**: без обращений к БД, на вход путь/байты, на выход dataclass'ы и список ошибок. Запись в БД — отдельный импортёр.
3. **Импорт атомарен**: файл (или пачка файлов одной команды) применяется целиком в одной транзакции или не применяется.
4. **Схема БД меняется только миграцией Alembic** (новый файл в `migrations/versions/`, `down_revision` — текущая голова). Миграция должна работать и на Postgres, и не ломать `Base.metadata.create_all` в тестах.
5. **Права проверяются на сервере** (`require_admin` и т.п.); скрытие кнопок на фронте — только удобство.
6. Названия групп хранятся так, как написаны в файле расписания (только без лишних пробелов).

## Соглашения

- Идентификаторы, файлы, таблицы, колонки — английские. Тексты для пользователя, ошибки API, вывод CLI — **русские**.
- Комментарии и docstring — по-русски, коротко, только где неочевидно «почему».
- Python: аннотации типов, стиль как в соседних файлах.
- TypeScript: без `any`; стили — в `styles.css` рядом с похожими.

## Тесты

- Каждая задача — с тестами; бизнес-правила (разбор файла, импорт, сборка недели) — тесты обязательны, лучше до кода.
- Рабочие файлы расписания (`*.xlsx`) в гит не попадают. Для тестов парсера строй маленькие книги openpyxl прямо в тесте (во временной папке) с той же раскладкой, что у настоящего файла.
- Тесты не должны зависеть от сети, Docker и рабочей базы.

## Как выполнять задачу

1. Прочитай файл задачи и документы, на которые он ссылается.
2. Неясность — в «Вопросы к архитектору», делай только однозначную часть.
3. Пиши тесты, затем код. Не выходи за рамки задачи; заметил другую проблему — опиши в отчёте, не чини молча.
4. Прогони тесты бэкенда и `npm run build` фронта (если трогал фронт) — всё зелёное.
5. Заполни в файле задачи раздел «Отчёт»: что сделано, какие файлы, как проверить, новые зависимости и команды, что вызывает сомнение.
6. **Не коммить.** Оставь изменения в рабочей копии: архитектор проверит дифф, перезапустит проверки и закоммитит сам.

## Поручения на чтение

Помощник получает работу, которую долго делать и быстро проверить (поиск по коду, где что используется, что сломается, контрольные числа).
- **Только чтение**: ничего не правь и не создавай в репозитории. Тесты запускать можно.
- Каждая находка — с доказательством: файл, строка, дословная цитата. Отделяй «проверено» от «не проверено, потому что…».
- Ответ — коротким списком в конце вывода.
